# claims-platform-test-automation

Test automation for ClaimPay, a small made-up healthcare claims and payments app that lives in this repo. The app is the thing under test; the tests and the decisions behind them are the point.

**Status:** being built in stages. This README only describes what exists today and will grow as each stage lands.

## Run it

You need Docker.

```bash
docker compose up --build
```

The app comes up on http://localhost:3000. The API is under `/api`; `/api/health` is a quick check.

Demo accounts (password `claimpay-demo`): `adjuster@claimpay.test`, `silver.member@claimpay.test`, `gold.member@claimpay.test`.

To run the app outside Docker against a local Postgres: copy `.env.example` to `.env` and edit `DATABASE_URL`, then `npm ci`, `npm run db:migrate`, `npm run db:seed`, `npm run dev`. The scripts read `.env` themselves (Node's `--env-file-if-exists`), so nothing needs exporting.

The app and database ports are bound to `127.0.0.1`. The demo ships with known credentials and a known signing secret, so it is not meant to be reachable from other machines as is.

## API

| Method | Path | Who | What |
|---|---|---|---|
| GET | `/api/health` | anyone | Status and the server's date (used for service-date rules) |
| POST | `/api/session` | anyone | Sign in, returns a bearer token |
| GET | `/api/procedure-codes` | anyone | The published procedure code list |
| POST | `/api/members` | adjuster | Enroll a member |
| POST | `/api/claims` | member | Submit a claim |
| GET | `/api/claims` | member, adjuster | Members see their own; adjusters see all |
| GET | `/api/claims/:id` | member, adjuster | One claim |
| POST | `/api/claims/:id/decision` | adjuster | `APPROVE`, `DENY` or `PEND` |
| POST | `/api/claims/:id/payment` | adjuster | Record payment; requires `Idempotency-Key` |
| GET | `/api/claims/:id/payment` | member, adjuster | The payment for a paid claim |

Every response carries an `X-Correlation-Id` header. Send your own to follow a request through the logs.

## The UI

Two roles, one page. A member signs in, submits claims and sees decisions and payments. An adjuster sees the queue, decides claims and records payments. It is written to be accessible first: real labels, field errors tied to their inputs, focus moved to the first problem, a live region for results, keyboard-reachable everything. The UI's only path to the API is [app/public/api-client.js](app/public/api-client.js). The contract tests, when they land, will run that file rather than a copy of it.

## Tests

```bash
npm test
```

**Unit** (`tests/unit`): the rules that don't need a database. The payment tests read their expected values from the worked-examples table in `docs/business-rules.md` at run time, so the document is the oracle and can't drift from the tests. Two deliberate mutations were run while writing them: truncating instead of rounding half up fails 5 tests; allowing SUBMITTED → PAID fails 2.

**API** (`tests/api`, needs a database): the real app, started in-process on a random port, with direct database access to check what was saved. Access rules (R1), every validation boundary (R2), the full status matrix through the real endpoints with the row checked after each move (R3), all 13 payment examples end to end against the saved row (R4), and idempotency including five concurrent requests with one key and two claims racing for one key (R5). One case starts the app with the planted defect on and expects exactly the half-cent rows to be short.

**Contract** (`tests/contract`, needs a database): what the UI sends and the least it needs back, as a Pact contract.
- `consumer.test.ts` runs the UI's actual `app/public/api-client.js` against a Pact mock and writes `pacts/claimpay-web-claimpay-api.json`. Nine interactions: sign-in (good and bad), procedure codes, claim submission (valid and invalid), listing, decision, payment, payment lookup.
- `provider.test.ts` starts the app in-process on a random port, sets up each "given" state by inserting rows with the fixed IDs the contract uses, and replays every interaction against it.
- CI fails if the committed contract differs from what the consumer tests generate, so the file in `pacts/` is always the real one.
- Checked by breaking it: renaming the `fields` key in validation errors on the provider fails verification with "Actual map is missing the following keys: fields". Reverted.

Pact's own OpenAPI-style response checking is deliberately not used here. The contract says what the UI depends on, which is narrower than everything the API returns, and that is the point.

**End to end** (`tests/e2e`, Playwright, needs a database): what a member and an adjuster actually see and do. 17 tests.
- Test data goes in through the API (`tests/e2e/fixtures/api.ts`). Each test gets its own member, named after the worker, so four workers never touch each other's rows. The suite was run five times in a row with four workers before this landed: 85 passes, 0 failures, about 17 seconds a run.
- No hard waits. Every assertion is a web-first `expect`. To prove it, the suite was run against the app with `DEMO_LATENCY_MS=400` (every API response 400ms slower): 17 passes.
- Expected amounts in the UI come from the worked examples in the rules: row 3 (`$6.70`) and row 9 (`$22.55`), the half-cent cases. Run against the app with `DEMO_DEFECT=payment-rounding`, exactly those two tests fail (`$6.69`, `$22.54`) and the other 15 pass.
- Retries: one in CI, none locally. A test that passes on retry is reported as flaky, never as passed.
- On failure the report carries the trace, a screenshot, and the list of API calls the page made with their correlation IDs, so the failing step can be followed into the server log and the database.
- Accessibility: axe on five page states, tab order, 320px reflow. What was checked by hand is in `docs/accessibility.md`.
